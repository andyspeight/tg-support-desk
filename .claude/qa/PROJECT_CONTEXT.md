# Project Context — TG Support Desk
_Generated by qa-sentinel on 2026-06-26. Edit freely; the skill reads this every run._

## What this project is
An AI-first B2B support desk (replacing Zendesk) for Travelgenix, supporting ~300 travel-trade clients. Every inbound query is handled by a server-side AI resolution agent (KB RAG + client context + past-ticket retrieval, with guardrails); humans only see a ticket after the AI has tried, diagnosed, and prepared a handover. Channels: email (Gmail API) and an SSO-gated client portal. Multi-tenant from day one (`tenant_id` on every table). Currently pre-go-live, running in **shadow mode** (AI drafts into internal notes rather than emailing customers).

## Trust boundaries
- **Server-side (may hold secrets):** everything under `src/app/api/`, all `"use server"` actions, `src/lib/**` (marked `server-only`), Supabase access via **service-role key only** (`src/lib/db/client.ts`). Anthropic / Voyage / Airtable / Gmail keys are server-only env vars.
- **Client-shipped (public):** `src/components/*` client components, the built `.next` bundle. **No `NEXT_PUBLIC_*` vars exist** — nothing secret is public-prefixed. No client-side Supabase SDK / anon key usage.

## Sensitive assets
- Secrets/keys: `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY`, `VOYAGE_API_KEY`, `AIRTABLE_PAT` (read-only Clients base), `GMAIL_CLIENT_ID/SECRET/REFRESH_TOKEN`, `CRON_SECRET`, `CSAT_SECRET` — all server-only env, `.env*` gitignored.
- PII: requester names/emails, ticket bodies, client records (Airtable), attachments. Stored in Supabase + Supabase Storage.
- Money/payments: **none in-app** — but the AI must never make commercial commitments (refunds/credits/contracts) — guardrail-enforced escalation.
- Paid-per-call APIs (budget risk): Anthropic (resolution agent + copilot), Voyage (embeddings/rerank). Cost-drain is the main DoS vector.
- Write access to data: tickets/messages/KB/notifications via server actions + cron routes.

## Attack surface (public/anonymous entry points)
- **API routes:** `/api/cron/*` (Bearer `CRON_SECRET`), `/api/ai/resolve` (Bearer `CRON_SECRET`), `/api/notifications/unread-count` (agent session), `/api/attachments/[messageId]/[index]` (agent/portal, signed storage URL).
- **Portal (SSO-gated, but client-facing):** `/portal`, `/portal/new`, `/portal/ticket/[id]` + server actions `askAction`, `raiseTicketAction`, `replyAction` (rate-limited).
- **CSAT:** `/csat` — signed-link survey (HMAC via `CSAT_SECRET`), unauthenticated-by-design.
- **Inbound email:** Gmail API **polling** (not a public webhook) — sender-verified, blocklist, loop-guard, HTML sanitised.
- Forms / user input: reply composer, internal notes, KB editor, portal ask/new/reply, settings, canned responses, tags.
- File uploads: agent reply/note attachments + portal ticket attachments (allowlist + size cap + signed URLs).
- User-generated content rendered to DOM: email HTML (sanitised via `sanitizeEmailHtml`), ticket/message bodies, KB article bodies.

## Critical invariants (must never happen)
- No secret ever reaches the client bundle (upheld: no `NEXT_PUBLIC_*`, service-role server-only).
- A portal user must never read or reply to another user's/client's ticket (IDOR — verify ownership scoping on `/portal/ticket/[id]`, `replyAction`, attachment fetch).
- An unauthenticated request must never reach an agent-only route/action (every `"use server"` action and `(app)` route calls `requireAgent()`/`getSession`).
- The AI never invents facts or makes commercial commitments; user/email content goes in the `user` role, never spliced into the system prompt (prompt-injection).
- A reply/action never crashes the request or silently fails to deliver without telling the agent (recent hardening).
- Airtable `filterByFormula` is never built from raw unescaped user input (injection).
- Money/role/owner fields are never trusted from client input (mass-assignment).
